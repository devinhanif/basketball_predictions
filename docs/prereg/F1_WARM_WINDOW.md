## The rule in eight lines (as it would be frozen)
1. **Question.** Production's props frame is built from `nba.duckdb` alone, so its 2022 rows are cold (32.6% of 2022 rows have a different `n_out_rot` than a history-inclusive build, adversary F1) and its training window starts 2022-10-01, which gives the first 2023 refit one season of rows (25,110). Does the same production code, on a frame built over history + `nba.duckdb` in one `build_features` and trained from 2019-10-01, lower integer-support CRPS?
2. **Arms (three fits; one confirmatory contrast).** **A** = production as it is: cold frame, rows from 2022-10-01. **B** = warm frame, rows from 2022-10-01 (descriptive). **C** = warm frame, rows from 2019-10-01 (the claim). Confirmatory: **C minus A**. Descriptive, no verdict: B minus A (what the warm features alone do) and C minus B (what the longer window alone does).
3. **Stats, family.** pts, reb, ast, fg3m (the production heads). BH at q = 0.05 over **m = 4** (C minus A, four stats) within each season; a stat passes only if it passes in 2023 AND in 2024.
4. **Metric.** Integer-support CRPS (199-point grid, `ceil(q - 0.5)`) for EVERY arm; played rows with `n_prior >= 5` **under the production (cold) frame's count** (27,619 / 27,701 rows), the identical `(game_id, player_id)` keys in every arm; paired difference; 95% percentile bootstrap clustered by `game_id` (2000 draws, seed 0), date clustering reported.
5. **Floors (improvement required, stat-specific).** pts **-0.005**; reb, ast, fg3m **-0.0025** (reason below). A stat-season passes when C minus A <= floor, CI upper < 0, BH-adjusted p <= 0.05, and every guard holds.
6. **Mixture.** All three arms are the production recipe end to end: stat heads AND the lower-tail mixture (`pi` and `w_q`) refitted inside each month block on that arm's own frame and window (option (i) of WOWY_STRUCT E7(b)). Nothing from the stored cold-frame arrays enters a verdict arm; they are a reproduction check for A only.
7. **Guards (each stat, each season).** (G1) PIT coverage at tau 0.10 / 0.20 / 0.80 / 0.90: |cov_C - tau| <= |cov_A - tau| + 0.01; (G2) `pi` ECE no worse than A by > 0.005; (G3) slices with n >= 300 not worse than A by more than 2 x |floor| (pts +0.01, others +0.005); (G4) planted-future and NULL-rule tests; (G5) reproduction checks (A reproduces stored production; C versus WOWY's `A0_warm` per R2 is a cross-check).
8. **A pass is a CANDIDATE.** It is not a production change (below). A null is closed: no other windows, frames, weights or stats under this id.

## Hypothesis
H1: a model trained on 2019-10 onward, whose long-window features and OUT sets are built with the pre-2022 history behind them, forecasts 2023-24 props better than production's. Counter-hypothesis stated first: HISTORY_WINDOW_3 (T420-T423) tried the training-row half of this and found a 2023 gain that did not replicate in 2024; the older seasons are worth about one current season and stop mattering once two current seasons exist. By 2024 production already trains on two to three current seasons. The expected result is a 2023-only gain and a 2024 tie, which fails.

What F1 adds that HISTORY_WINDOW_3 did not have (this is why it is a new question and not a re-run): (a) the warm frame, i.e. features and OUT sets with history behind them, which is a different input, not just more rows (feature shift table below); (b) 2021-22 included, and the history rows carry their REAL injury reports (HW3 set them missing and left 2021-22 out); (c) the mixture refit on the longer window. What it still shares with HW3: the 2023 select season trains on one season in production, so "window cut to one season" (the reversal condition written on 2026-10-11) is literally the situation of the early 2023 blocks.

## Metric, inference, pass rule
For each stat s and season t, delta = CRPS(C) - CRPS(A) on the same keys. Pass: delta <= floor_s, 95% game-clustered CI upper < 0, two-sided bootstrap p BH-adjusted over the four stats within season t <= 0.05, and G1-G5. **Code path (review edit 4):** CI and draws from `nba/props/metrics.py::paired_score_delta_ci` (via `_clustered_boot_means`) as it stands at the freeze commit; two-sided p = min(1, 2 x (1 + #{draws with mean delta >= 0}) / 2001) with 2000 draws, seed 0; the stored reference for R1 is `research/eval/recent_role_full_eval.py::stored_reference`; the harness is `research/eval/f1_warm_window_run.py` and its frame builder is the gate's `build()` unchanged (a second builder is a second treatment). A stat is CONFIRMED when it passes in 2023 and in 2024. **Verdict:** PASS if >= 1 stat is confirmed and no stat is HARM; FAIL otherwise. HARM = delta >= +|floor_s| with CI lower > 0 in either season for any stat; any HARM fails the verdict (one rule, no per-stat rescue). Slices, B minus A, C minus B, per-block and early-season results are guards or descriptions only: they cannot create, rescue or qualify a pass, and a gain present in 2023 only is reported as FAIL. Reported, no verdict: B minus A, C minus B, continuous-quantile scores (never compared to the grid), date-clustered CIs.

**Why these floors (protects against: calling a p-value a result; a floor below the noise).** The house floor is -0.005 for pts. For the count stats the paired CI half-widths of the closest comparison (T420/T421) are 0.0009-0.0020 (reb, ast, fg3m) versus 0.0037-0.0049 (pts), so -0.005 would sit 2-5 times above what the count stats can resolve and the family could never pass on them for a reason unrelated to whether the change helps. The floor is set at the same ratio to noise as the pts floor: 1.25 x the 80%-power MDE that HISTORY_WINDOW_3 stated for this design before its run (pts about 0.004, giving 0.005; reb, ast, fg3m about 0.002, giving 0.0025), fixed from widths, not from effects. (The later power table uses inflated widths and so reports larger MDEs; the floors are not re-derived from them.) A smaller floor would let noise pass; the interval and the BH step still apply.

## Multiplicity
One confirmatory arm x four stats = **m = 4**, BH within each season, 2023 and 2024 each. Choosing the two-arm design (B and C both confirmatory) would make m = 8 and let a thin B result borrow weight from the bundle; I recommend one arm because the production decision is the bundle (Devin: warm and 2019 together), C minus B and B minus A are free to compute and are reported as decomposition only. They cannot rescue or sink the verdict.

## Calibration and mixture guards
G1: randomised PIT on the 199-point pmf (order game_date, game_id, player_id; seed 0), coverage of P(PIT < tau) at tau 0.10 / 0.20 / 0.80 / 0.90 with |cov_C - tau| <= |cov_A - tau| + 0.01 (distance to nominal, not difference from A, so a better-calibrated C is not failed), per stat and season. ## Reproduction and run-time STOPs (checked by the harness before a verdict is printed)
R1: A refit by the harness reproduces the stored production forecasts' integer CRPS (`research/eval/recent_role_full_eval.py::stored_reference` on the stored lower-tail components): 2023 within 1e-4 and 2024 within 2e-4 per stat (the stored 2024 arrays pre-date the neutral-site restoration of five 2024 games, so 2024 gets the wider band, as WOWY_STRUCT). If A does not reproduce, the comparator is not production and the run stops. R2 (review edit 2): the verdict uses the C arrays produced by the F1 harness (`research/eval/f1_warm_window_run.py`, to be written after the freeze, at the freeze commit's code), never a choice between two C arrays.
