## Item 1 — `nba/coldstart/archetypes.py` + `nba/props/opponent.py` (feature-source caching)

**Verdict: safe to commit.**

- Traced the as-of discipline by hand:
  - `build_player_shot_rates`/`build_player_reb_ast_rates` (`nba/features/player_possession_features.py`,
    `nba/features/player_rebound_assist_features.py`) already return **one row per
    historical game**, each row itself a strictly-prior cumulative window
    (`ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING`). They are date-independent in
    the sense that running them once returns the *entire* history; no as-of filtering
    happens inside them.
  - The as-of filtering happens downstream, in `_latest_tendencies_as_of`
    (`nba/coldstart/archetypes.py:372`), which does `df.filter(pl.col("game_date") <
    pl.lit(as_of_date)...)` **before** taking each player's latest row. This filter is
    unchanged by the refactor — it is still applied once per `as_of_date`, just against
    an already-fetched frame instead of a freshly-queried one.
  - Caching (`PlayerFeatureSource`, `build_player_feature_source`,
    `build_player_feature_frame_cached`) therefore does not change *which rows* are
    visible to a given `as_of_date` — it only avoids re-running the same full-history
    SQL query redundantly. This is a pure perf refactor, not a semantics change: the
    future-game leakage surface (filtering happens before, not after, caching) is
    unaffected.
  - Age (`_apply_asof_age`) is correctly kept **outside** the cached, date-independent
    part and recomputed per `as_of_date` (it is the one genuinely date-dependent static
    field) — confirmed at `nba/coldstart/archetypes.py:361-376`.
- Equivalence proof quality: `tests/props/test_opponent.py::test_cached_feature_source_matches_per_date_query`
  and `::test_assign_archetypes_over_dates_matches_naive_per_date_path` both build real
  history (`_build_archetype_opponent_history`, two opponents with different ret/reb
  profiles) across 11 distinct dates and assert `old.equals(new)` / `naive.equals(fast)`
  row-for-row — not just "both ran without raising." This is a genuine proof of
  equivalence, not a smoke test.
- No-leakage proof quality: `test_archetype_factor_no_leakage_future_game_does_not_change_factor`
  plants a wild future game (`"2023-12-01"`, extreme reb=99/pts=300) for the *same*
  opponent team used by an earlier target game and asserts the target's factor is
  unchanged before/after. Combined with the team-level analog
  (`test_no_leakage_future_game_does_not_change_factor`), this directly tests the
  scenario the task flagged as critical.
- Ran `tests/props/test_opponent.py` (14 tests) green.

**Minor (non-blocking) observations:**
- `_latest_prior_tendencies`/`build_player_feature_frame` (the old single-date
  entrypoints) are kept as thin wrappers rather than removed — correct call per the
  docstrings (other single-shot callers like `build_player_archetypes`'s one-time
  ref-date fit still use them), not dead code. No action needed.
- `build_player_feature_source` re-fetches `shot_rates`/`reb_ast_rates` fully in Python

## Item 2 — `nba/props/metrics.py` + `nba/props/run.py` (clustered bootstrap)

### 2a. `cluster_ids=None` backward compatibility — **safe, verified**
`mean_bias_ci`/`paired_score_delta_ci` both short-circuit to the original
`bootstrap_ci(..., stat_fn=np.mean, ...)` call when `cluster_ids is None` — identical
code path to before the patch, byte-for-byte (confirmed by
`test_cluster_ids_none_is_unchanged_backward_compatible_default`, which compares the
explicit-`None` call against the no-kwarg call and asserts `lo`/`hi`/`point` equal).

### 2b. `cluster_ids` / `valid_mask` alignment in `run.py` — **safe, verified**
- `game_ids_full = target.select("game_id")...` (`nba/props/run.py:343`) is built from
  the same `target` frame, in the same row order, as `y`/`pred_mean`/`dates_full` used
  to build `valid_mask` inside the per-stat loop — confirmed by reading
  `y = target.select(stat)...` a few lines above and `valid_mask =
  np.isfinite(y) & np.isfinite(pred_mean)` (`run.py:423`). `game_ids_m =
  game_ids_full[valid_mask]` (`run.py:438`) therefore indexes the identical boolean mask
  applied to `y_m`/`pred_mean_m`/`dists_m` — no reordering, no stale mask reuse across
  stats (recomputed every loop iteration since `y`/`pred_mean` differ per stat).
- Combo path (`_build_combo_results`, `run.py:765`): `game_ids_c_m = target.select(
  "game_id")...to_numpy()[valid_mask_c]` is computed inline against `valid_mask_c`
  directly rather than reusing a module-level `game_ids_full` — also correct, just a
  different (equally valid) construction pattern. No divergence found between the two.

### 2c. Statistical validity gap — **MAJOR, unresolved, should be fixed before relying on these CIs**
`_bootstrap_ci_clustered` (`nba/props/metrics.py`) sets its "insufficient data" /
reliability note using `n = len(values)` (the **row** count, i.e. player-games):
```python
note = "" if n >= MIN_RELIABLE_N else f"insufficient data for a reliable CI (n={n})"
```
For a cluster bootstrap, the quantity that governs whether a bootstrap CI is reliable
is the **number of clusters** (`g`, e.g. distinct `game_id`s), not the number of rows.
A 5-game slate with 10 players each gives `n=50` (clears `MIN_RELIABLE_N=30`, no
warning) but only `g=5` independent clusters — a cluster bootstrap with 5 clusters is
known to be unreliable (too few resampling units to approximate the true sampling
distribution), yet this code reports it as reliable. `_clustered_boot_means` computes
`g` internally (`len(unique_clusters)`) but never surfaces it to the caller, so the
reliability note can't currently account for it.

**Failure scenario:** a props run with a short slate (e.g. 5-10 games, 40-80
player-game rows) passes `MIN_RELIABLE_N` on row count alone, reports a tight-looking
clustered CI with no caveat, and that CI is quoted as evidence a rung win/loss is real
when the effective sample size (games) is far too small to support that claim — exactly
the kind of "looks too good because of too few independent units" failure CLAUDE.md
asks to audit for.

**Fix suggestion (not applied — review only):** have `_bootstrap_ci_clustered` compute
`g = len(np.unique(cluster_ids))` and gate the note (and ideally `MIN_RELIABLE_N` itself)
on `g`, not `n`; `_clustered_boot_means` already computes this value and could return it
alongside the resample array.

### 2d. Test quality — **good, with one gap**
`tests/props/test_clustered_bootstrap.py` has solid coverage: CI strictly widens under
planted within-game correlation (both `mean_bias_ci` and `paired_score_delta_ci`),
singleton-cluster degeneracy matches the iid path exactly (good regression anchor),
seed-determinism, `None`-default equivalence, and a negative test for mismatched
`cluster_ids` length. **Missing:** no test exercises the few-clusters-many-rows-per-cluster
scenario from 2c (e.g. `g=3` clusters, `n=100` rows) to check whether the reliability
note fires appropriately — would have caught the gap directly.

**Status note:** the task description says this is "being added right now by another
agent (may be mid-flight)" — the above is the state found on disk at review time; if
`g`-based gating is added afterward, 2c should be considered resolved and this note
stale.

## Item 3 — rung-4 possession step-heads (`nba/features/possession_step_features.py`,
`nba/models/rung4_stepheads.py`, `nba/models/colab/*`)

**Verdict: safe to commit; no leakage found; chronological split confirmed.**

### As-of / no-lineup-cheating check (CLAUDE.md risk #3) — **passed**
- Training features (`POSSESSION_STEP_FEATURE_COLUMNS`) are: `period`, `clock_start`,
  `score_diff` (intra-game state known before the possession's own outcome — confirmed
  the parser captures `score_diff` entering the trip, before this trip's own points,
  `nba/parse/possessions.py::start_trip`), plus `off_*_prior`/`def_*_prior`/
  `league_avg_ppp_asof` from `build_team_possession_rates`, itself a strictly-prior
  cumulative window over **that team's own earlier games** — confirmed at
  `nba/features/possession_features.py:184-237` (fills nulls with documented league
  defaults rather than leaking a null/zero that would behave differently).
- **No actual box-score minutes or lineups appear anywhere in the feature set.** The
  team ratings are game-level aggregates entering the game, not updated mid-game and
  not derived from who is actually on the floor. `StepHeadsRung.predict()`
  (`nba/models/rung4_stepheads.py:348`) only consumes `PREDICT_FEATURE_COLUMNS`
  (matchup-level as-of team ratings), substituting a documented *neutral* intra-game
  context (`_NEUTRAL_PERIOD`/`_NEUTRAL_CLOCK_START`/`_NEUTRAL_SCORE_DIFF`) rather than
  any real game state — there is no path by which this rung's `predict()` could see
  real lineups/minutes even by accident, since it never reads `player_game_stats` or
  `stints` at all.
- Labels (`outcome`, `shot_zone`, `made_shot`, `oreb`, `duration_s`) are the
  possession's own realized result and are never fed back as features — confirmed by
  reading `build_possession_step_training_frame`; the five label columns are added
  via `.with_columns` after the join and kept in a separate `POSSESSION_STEP_LABEL_COLUMNS`
  list from `POSSESSION_STEP_FEATURE_COLUMNS`, with no overlap.

### Train/val/holdout split — **chronological, confirmed**
The split lives in `nba/models/colab/rung4_stepheads.ipynb` (the local repo only ships
the export script + model code; training happens off-box per the memory-budget
constraint, which is appropriate and documented). Read the notebook cells directly:
```python
holdout_season = HOLDOUT_SEASON if HOLDOUT_SEASON is not None else df["season"].max()
tunable = df.filter(pl.col("season") < holdout_season)
holdout = df.filter(pl.col("season") == holdout_season)
...
dates = tunable.select("game_date").unique().sort("game_date").to_series()
cutoff = dates[int(len(dates) * 0.85)]
train_df = tunable.filter(pl.col("game_date") < cutoff)
val_df = tunable.filter(pl.col("game_date") >= cutoff)
```
This is a genuinely chronological split at two levels (season-level frozen holdout,
then date-level train/val inside the tunable seasons) — no `train_test_split`, no
shuffling before splitting, consistent with CLAUDE.md's "walk-forward by date" and
"one frozen final holdout season" requirements. I could not *execute* the notebook
(Colab/GPU, out of scope for this box per the task's own constraints) so I could not
verify runtime behavior beyond static reading, but the split logic itself is
unambiguous from the source.

**Minor:** the notebook is "self-contained" by design (classes/constants duplicated
from the main repo, per its own docstring, so Colab doesn't need the private repo
cloned). This is a deliberate, documented tradeoff, but it is a drift risk — if
`POSSESSION_STEP_FEATURE_COLUMNS` or `OUTCOME_CLASSES` changes in
`nba/features/possession_step_features.py` without the notebook being updated in
lockstep, a stale notebook would silently train on the wrong feature order. No
automated check enforces the two stay in sync (acknowledged by the notebook's own
docstring: "must be kept in sync... by hand"). Not a leakage issue, but worth a
tripwire test (e.g. a test asserting the notebook's duplicated constant lists match
the module's, parsed from the `.ipynb` JSON) if this rung becomes load-bearing.

**Not wired into eval harness / registry yet** (`nba.eval.run.RUNG_SPECS`) per the
module's own docstring — correctly scoped as "ships the contract, not yet gated,"
consistent with CLAUDE.md's model-gate-before-promotion rule. No premature promotion
found.

### Scope creep check — **none found**
- No new dependencies: `torch`, `scipy.stats.norm`, `polars`, `duckdb` are all already
  in the CLAUDE.md stack.
- `StepHeadsRung` implements the existing 3-method `RungModelBase` contract — no new
  abstraction invented.
- `predict()`'s Normal-CDF margin approximation is explicitly documented as a stopgap
  ("NOT a full possession simulation... that wiring is a follow-up milestone") rather
