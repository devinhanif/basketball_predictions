# PROPOSAL: export fields the honesty pages need (app/api lane C2a, 2026-11-17)

Status: proposal only. Nothing in `nba/` was changed; every `nba/` location below was found by reading the main
checkout, not by running it. Adding any of these is an `nba/export` change (live path: Devin's go, replay oracle).

Why none of these is derived in the app: the app never computes a probability, edge, price, eligibility or model
output (docs/APP_SECURITY_BASELINE.md, CLAUDE.md "markets are a prior"); a value the engine did not store would be the
app's own claim, unaudited and outside every pre-registration.

| # | field | page it unblocks | where `nba/` holds it (read only) | why the app cannot derive it |
|---|---|---|---|---|
| 1 | **odds capture status per book** (last attempt time, ok/failed, HTTP status or reason, rows inserted) | health strip | `nba/odds/capture.py:139-151` (`CaptureReport`: `requests_used`, `inserted`, `reasons`, `unreachable`, `store_failed`), `run_capture` at :190-215 | the export holds quotes, not attempts: a book with no quote may have failed (the 11-14..11-16 `401 DEACTIVATED_KEY` nights) or posted nothing; the strip can only say "newest quote in this export" |
| 2 | **per-row `stale_model` flag on every forecast row** | record, health strip | AVG rows: `forward_avg_shadow.stale_model` (`nba/daily/avg_shadow/bundle.py:100`, read by `nba/export/best_model.py:166, 76-87` into `freshness`); production rows: no writer of such a flag was found | only AVG rows carry `freshness`; production staleness (e.g. a missed refit) is not stored, and guessing it from `fit_through` would be the app's rule |
| 3 | **forward-test counts** (test id, arm, stat, eligible paired n, distinct dates, as_of; counts only) | forward-test tracker | `nba/daily/checkpoint.py` (look detection by distinct-date count, docs/FORWARD_PREREG_2026_27.md:294-295), `forward_scores_elig` (`nba/daily/settle.py:264, 340`) | the tracker now counts `settled_scores` rows (latest-row rule) per arm, which is not the tests' paired, T-60 eligible count; pairing rules (same run_id, T-30 snapshot) live in the scorer |
| 4 | **independent-legs joint probability beside the copula one** on each parlay record | parlay diagnostics | engines `independence` / `gaussian_copula` / `t_copula` (`nba/parlay/__main__.py:58`; `JointModel("independence", ...)` at `nba/parlay/analysis.py:372`) | each `evaluate_<date>.json` record carries one `raw_model_prob` from one engine; multiplying leg chances in the app would be a new model output (and wrong for same-player legs) |
| 5 | **T-60 eligibility per scored row** (`forward_scores_elig`, or a `t60_eligible` flag plus the eligible row's made_at) | scorecard | `nba/daily/settle.py:264` (table), `:340` `settle_eligible_pending` | the export's `settled_scores` is `forward_scores`, latest row regardless of lead (`nba/daily/settle.py:88-120`); tip-off is exported only for the 7-day lookback, so 48,292 of 99,534 rows on the frozen export cannot be checked |
| 6 | **tip-off for every settled game** (season-long `game_id, tipoff`) | scorecard (T-60 check where #5 is absent) | `nba/export/reader.py:49-53, 181` reads forecasts (and so tip-offs) only for the lookback window; `games` in `nba.duckdb` holds all | without it the scorecard keeps unverifiable rows, labelled |
| 7 | **integer-support CRPS (`rps`), `pinball19`, PIT bounds, q10/q90 hit** per eligible row | scorecard | `forward_scores_elig` columns (`nba/daily/settle.py:264-418`; FORWARD_PREREG_2026_27.md amendment 2026-10-09) | the app does not re-score stored grids against outcomes (that is a scoring rule, and would pair a forecast with an outcome inside the LINE_CAL_LIVE window) |
| 8 | **market probability per scored row** (de-vigged, book, snapshot time) | scorecard (market column) | `nba/forward/scorecard.py:63` (`devig`), `:370`, `:445` (`p_over_devig` per line), `:499-513` (pairing with picks) | the app does not de-vig; prop CRPS rows have no line, so a market P(over) is a different scored object and needs the engine's pairing |
| 9 | **CLV** per pick (pick price, closing mid, difference in cents) | scorecard / track record | `nba/jarvis/book.py:607` (`clv = mid - price`, cents), `:745`, `:852` | no pick ledger or closing price is in the export |
| 10 | **"what moved it"**: the stored components of a prop mean (`mean_recency`, the residual head's part, `mean_sim`) as explicit fields, and any per-feature contributions | distribution / record | `prediction_json` already carries `mean_recency`, `mean_sim`, `mean` for production rows (`nba/props/forward.py`, keys listed in the export); no per-feature contribution writer was found | `mean - mean_recency` would be the app's arithmetic on model internals; contributions do not exist anywhere read |
| 11 | **"why this label"** reasons (JARVIS play label and its reason text) | record / desk explanations | `nba/jarvis/slate.py:171` (`Play.reason`), built at `:209-247` | the label is JARVIS's decision with its own gates; re-deriving it in the app would fork the rule |

Order of value (opinion): #5/#6 first (the scorecard's main limitation), then #3 (the tracker's honest n), #1 (the
strip), #4 (parlay diagnostics are empty today: all 1,355 records on 2026-11-16 are one-leg `marginal`).
