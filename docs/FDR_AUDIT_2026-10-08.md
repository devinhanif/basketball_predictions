# FDR / Methodology Audit — 2026-10-08 session

_Statistician pass over every A/B claimed this session. Re-derives p-values where the
artifact has a numeric CI; flags everywhere a numeric CI was not committed to the repo
(point estimates / checkmarks only) as **not independently re-derivable** — per the
"re-derive, don't trust" rule, I did not just accept markdown checkmarks as evidence._

## 0. First finding, before the table: the bootstrap's own correctness

`nba/eval/metrics.py::bootstrap_ci` (used by every CI in this session via
`nba/props/metrics.py::paired_score_delta_ci`) resamples **row indices of the
already-paired per-player-game delta array** — i.e. the resampling unit is one
player-game, not one game. Multiple players from the same game are highly correlated
(same pace, same blowout/garbage-time, same foul-outs, shared minutes-redistribution
shocks). Resampling at the player-game level treats those correlated rows as
independent draws, which **understates the true standard error and makes every CI in
this report too narrow** — i.e. more "wins" look significant than really are. I found
no grouped/cluster (by `game_id`) resampling anywhere in `nba/eval/metrics.py`,
`nba/eval/model_routing.py`, or `nba/eval/routed_eval.py`. **This is the single
biggest inference risk in the whole session's results**, and it affects every CI below
in the same direction (anti-conservative). I did not have per-row arrays to re-run a
game-clustered bootstrap myself (would need the real DB; out of scope per my operating
constraints), so I can't quantify how much narrower the reported CIs are than they
should be — only flag the direction of the bias.

### Family C — Volatility-bucket routing grid (3 stats × 5 classes = 15 cell-tests)

RESULTS_2026-10-08.md §2 reports only checkmarks ("SIM ✅" / "SEASON-AVG ✅" / "tie"),
**no numeric CI bounds for any of the 15 cells** — the markdown table is the only
artifact; there is no committed JSON/CSV of the per-cell `ConfidenceInterval` objects,
and `nba/eval/model_routing.py`'s real-DB assembly is explicitly "the maintainer's job,
not run by this agent" (its own docstring) — i.e. **the numbers in RESULTS.md were
never saved as a reproducible, inspectable artifact in this repo.** I could not
re-derive a single one of these 15 p-values. What I can say:

- 8 of 15 cells are reported as CI-excludes-0 "wins" (pts: insufficient_history,
  intermittent, smooth(season-avg); reb: insufficient_history, intermittent, erratic;
  ast: intermittent, erratic).
- Per-bucket sample sizes are necessarily smaller than the n≈600-game overall sample in
  Family A (5-way split of the same player population), so per-bucket CIs are
  mechanically **wider** than the overall CIs — and in Family A, even rebounds barely
  clears m=3 correction and points/assists don't clear at all. It would be
  mathematically inconsistent for most of these 15 narrower-sample cells to be *more*
  significant than the overall-sample numbers feeding into them, unless the bucket
  effect sizes are much larger than the pooled effect (plausible for the
  cold-start/intermittent cells specifically, since that's the documented mechanism;
  implausible for all 8 uniformly).
- **BH over m=15 (or more, once combined with Family D below) requires a materially
  smaller p than m=3 to survive at the same q** — at minimum p ≤ 0.0033 for the single
  best-ranked cell at q=0.05. Without the numbers I cannot confirm any cell clears
  that bar.

**Verdict: PROVISIONAL, all 15 cells.** The qualitative pattern (sim wins concentrate
in cold-start/intermittent/erratic, season-avg wins "smooth") is internally consistent
and replicates loosely across 3 correlated stats, which is suggestive, not confirmatory
— but as reported, none of these 8 "wins" can be certified as BH-survivors because the
underlying numbers were never retained. **Action item for next session: commit the
per-cell `RouteBucketResult`/CI objects (JSON) when this is next run, not just a
markdown checkmark table**, so a correction can actually be computed.

## 3. Frozen-holdout reuse check

- `nba/eval/ga_tune.py` (win-probability MOV-Elo GA tuning) is clean: `objective()`
  only ever sees `split_frozen_holdout(...).tunable_df`; the holdout season
  (default 2025) is carved out before the differential-evolution loop starts, and
  `evaluate_mov_elo_on_holdout` is a separate, explicitly-confirmatory call. No
  contamination found here.
- **The props/routing pipeline does not use `nba.eval.walkforward.split_frozen_holdout`
  at all** — I grepped `nba/props/run.py`, `nba/eval/player_points_sim_eval.py`,
  `nba/eval/player_reb_ast_sim_eval.py`, `nba/eval/routed_eval.py` for `holdout` and
  found nothing. The "walk-forward vs. holdout" split referenced in NEXT_SESSION.md
  (Family E above) for the routing analysis was therefore assembled **ad hoc by
  whoever ran the maintainer entry point**, not by the project's one canonical
  frozen-holdout mechanism — there is no committed code defining which season/date
  range that "holdout" actually was, so I cannot confirm it is even the *same* season
  carved out for Elo, nor that it was touched only once.
- **Concrete reuse risk, not hypothetical:** NEXT_SESSION.md item 3 says "Retest points
  routing at `n_sims=2000` — the out-of-sample points 'no-win' was partly Monte-Carlo
  noise ... a sharper sim could flip it." That is a textbook **"we saw it lose on the
  held-out data, so let's change the model and look again on the same held-out data"**
  loop. If the retest uses the same out-of-sample rows, a future "points now wins" will
  be a holdout-reuse-contaminated result, not an independent confirmation, no matter
  how clean the second run's own CI looks. **Recommendation (append to escalations if
  this is attempted): either (a) draw a *new*, previously-untouched slice (e.g. a later
  partial season once available) for the n_sims=2000 retest, or (b) if the same rows
  must be reused, report the result explicitly labeled "exploratory, holdout-reuse
  risk, not confirmatory" rather than as a clean win.**
- Minutes 1A's `learned_context_cal_frac=0.5` chronological split is internal to
  whatever rows the caller passes in; there's no evidence it specifically excludes the
  Elo frozen-holdout season, meaning season-2025 rows were likely included in the
  69,205-row "out-of-sample" minutes test too. That's fine in isolation (minutes isn't
  the same target as win-probability), but it means the *same* late season is now the
  de facto "holdout" for at least three different model families this session (Elo,
  minutes, and whatever routing/matchup runs also used late dates) — CLAUDE.md's own
  risk #2 warns against exactly this ("isn't silently reused across experiments, which
  re-inflates error"). **No single experiment is contaminated, but the season is
  accumulating mileage as an informal, repeatedly-consulted test set across unrelated
  model families, which erodes its value as a true held-out check over time.**

## 4. Power note — are the points/assists "ties" real nulls, or just underpowered?

Family A's overall points test has CI [−0.019, +0.043] on a point estimate of +0.011 —
width ≈0.062 CRPS units on a ~3.2 CRPS base (≈2% of the base metric). Assists: CI width
≈0.016 on a ~0.87 base (≈1.8%). These are not tiny CIs relative to Family A's rebounds
effect (−0.014, barely larger than the assists point estimate) — i.e. **the points and
assists tests are well-powered enough to have detected an effect the size of the
rebounds win, had one existed**, since their CI half-widths (≈0.031 for points, ≈0.008
for assists) are comparable to or smaller than the rebounds effect size itself
(0.014). So: **assists is a genuine near-null at this n** (CI half-width 0.008 is
smaller than even half the rebounds effect — if a rebounds-sized effect existed in
assists, it likely would have shown), while **points is more ambiguous** — its CI
half-width (0.031) is *larger* than the rebounds effect size, so a points effect as
small as rebounds' could hide inside this points CI undetected. That supports
NEXT_SESSION's own instinct that points may be under-detected (not proven-null) at the
current `n_sims=500`, more plausibly from **simulation variance adding noise to the
candidate's score** (inflating CRPS noise on the sim side specifically) than from
sample-size-driven estimation power on the bootstrap side — those are different kinds
of "power" and the fix (more `n_sims`) addresses the right one. The 15-cell bucket
grid (Family C) is almost certainly underpowered per-cell relative to the overall
tests, given smaller n per bucket and no numeric CIs reported to check — treat any
single-bucket "tie" there as "no power to conclude," not "no effect," by default.

## Bottom line — what we may still trust

- **CONFIRMED:** rebounds beats season-avg overall (p≈0.012, survives BH at q=0.05/0.10
  pooled with the only other numerically-testable claims); lineup archetype-mix is a
  real but tiny (R²≈0.016) non-additive effect (permutation p=0.004, survives BH);
  on-court usage regression (effect too large to be a CI-width artifact); minutes 1A
  gated version (large n=69,205, internally cross-validated against its own
  established-player regression before shipping); usage redistribution 2A/2B is a
  genuine inert null (n=0 restricted sample, nothing to correct).
- **PROVISIONAL, not yet BH-correctable:** all 15 volatility-bucket routing cells, the
  walk-forward-vs-holdout split numbers, and the matchup/opponent 4-stat deltas — none
  have numeric CIs committed to the repo, so none can be run through a real correction;
  treat their qualitative direction as suggestive, not shipped-grade evidence.
- **REJECTED as evidence (though the underlying ship/no-ship decision is probably still
  right):** the archetype-cluster "examples" sub-table (explicitly a curated subset of
  a larger, unreported grid — classic cherry-picking pattern) and the matchup-adjustment
  family (never passed through a bootstrap at all, in either run).
- **Biggest single risk:** the project's bootstrap resamples at the player-game level,
  not the game level, which is anti-conservative for every CI in every result above
  given same-game correlation across teammates — "CI excludes 0" should be read as
  weaker evidence than its face value everywhere in this session's work until a
  game-clustered bootstrap is substituted.
- **Holdout verdict:** Elo/win-probability holdout mechanism is clean and untouched.
  The props/routing side has no equivalent canonical mechanism, assembled its
  "holdout" split ad hoc and unrecorded, and is already flagged in NEXT_SESSION.md for
  a retest-after-seeing-the-result loop (points at `n_sims=2000`) that will contaminate
  it if run on the same rows.
